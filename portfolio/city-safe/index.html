프로젝트 개요

전기차 배터리 화재·과열·이상 감지 시스템의 백엔드입니다. 두 서버가 동일한 운영 가설인 “최신 상태 우선, 손실 허용, 영구 다운 금지”를 공유하도록 인터페이스와 장애 처리 정책을 맞췄습니다.

C++ 서버는 열화상 SDK, 프레임 수집, ROI 온도·이상 분석, WebSocket 스트리밍에 집중하고, Python 서버는 DB 영속화·집계, 외부 시스템 통합, 이벤트 영상 녹화, 캐시·상태 머신을 담당했습니다.

왜 패치가 아니라 재설계였는가

기존 구조에서는 카메라 대수가 늘수록 다음 증상이 더 자주 나타났습니다. 공통 원인이 공유 상태에 락이 대응되지 않는다는 한 가지였기 때문에, 개별 증상을 패치하는 방식으로는 회귀 위험이 컸습니다.

  • · 간헐적 프로세스 종료 — dangling 참조와 data race로 인한 access violation
  • · 프레임 손실·중복 조작 — 타임스탬프 맵의 무보호 동시 접근으로 판정이 비결정적
  • · 메모리 사용량 증가 추이 — 상한 없는 큐 적재와 객체 간 순환 참조
  • · 재연결 중 다른 카메라까지 응답성 저하 — SDK 동기 호출이 글로벌 락을 점유
  • · 검출 상태 불일치 — 모니터링 스레드와 스트리밍 경로가 같은 맵을 보호 없이 공유

그래서 “어떤 공유 상태를 어떤 락이 보호하는가”를 코드에서 눈으로 확인할 수 있는 구조로 바꾸는 것을 재설계의 목표로 잡았습니다. 아래 의사결정은 모두 이 목표에서 파생된 것입니다.

두 개의 기준 영역

데이터 영역 (C++ → Python, WebSocket): thermal·anomaly·flame·gas 이벤트를 publish 방식으로 push합니다. 유실이 허용되는 대신 최신성이 우선입니다.

제어 영역 (Python → C++, REST): 카메라·센서 connect/reconnect, ROI reload, mount_type 변경을 요청합니다. 정합성이 중요하므로 요청-응답으로 결과를 확인합니다.

IP 변경처럼 순서가 중요한 작업은 disconnect + connect를 따로 부르지 않고 C++ 측 단일 /reconnect 엔드포인트가 원자적으로 처리하도록 했습니다. 두 호출 사이에 다른 요청이 끼어들 여지를 없애기 위해서입니다.

스레드 모델 — 성격이 다른 작업의 격리

기존에는 단일 io_context와 단일 풀에서 모든 작업이 실행됐습니다. ROI 분석 같은 CPU 집약 작업이 네트워크 응답성을 잠식하는 구조였습니다. 작업 성격에 따라 전용 풀로 분리하고, 각 풀의 크기를 코어 수 기반으로 산정했습니다. 

16 코어 기준

io_context   ── IO 4    네트워크 · 타이머 (CPU 작업 없음)
ThreadPool   ── ROI 8   ROI 온도 분석 (CPU 바운드)
ThreadPool   ── enc 4   JPEG · Base64 인코딩 (CPU 바운드)

각 풀은 독립된 io_context와 work guard를 갖고, 소멸자에서 work 해제 → stop → join 순으로 정리됩니다. 기존의 detach()된 스레드는 종료 시점에 join이 불가능해 객체 수명과 결합되지 않는 문제가 있었는데, 이를 RAII로 묶었습니다.

운영 설계의 핵심 판단

  • · CPU 바운드 작업과 I/O 작업을 분리해 스레드 풀 구성
  • · 실시간성을 위해 오래된 프레임을 폐기하고 최신 프레임 우선 처리
  • · 느린 클라이언트로 인한 WebSocket 송신 지연 방지
  • · 재연결 시 백오프를 적용해 서버 부팅·장애 상황에서 재시도 폭주 방지
  • · 종료 시 단계적 graceful shutdown 후 강제 종료 fallback 적용

핵심 기술 의사결정

1. 공유 상태와 락의 1:1 매칭

증상

모니터링 스레드와 스트리밍 경로가 동일한 맵을 동시에 읽고 쓰면서, 검출 상태 불일치와 메모리 접근 오류가 발생했습니다.

원인

검출 상태·배경온도 등 10여 개의 unordered_map이 뮤텍스 선언 없이 멤버로 흩어져 있었습니다. 동시 insert로 rehash가 일어나면 다른 스레드가 들고 있던 참조가 전부 무효화됩니다.

선택

공유 상태를 하나로 응집하고 카테고리별 뮤텍스로 나눴습니다. 카메라별 상태에는 카메라마다 독립 락을 부여했습니다.

효과

어떤 락이 무엇을 보호하는지가 타입에 드러납니다. 카메라 A의 갱신이 카메라 B의 송신을 막지 않으며, 카메라별로 독립된 락을 사용해 카메라 수가 늘어나도 서로 간의 경합을 최소화했습니다.

struct PipelineState {
    struct PerCameraROI {
        mutable std::mutex mtx;                 // 카메라별 독립 락
        std::unordered_map<int, ROIData> rois;
    };
    mutable std::mutex roiMapMtx;
    std::unordered_map<int, std::shared_ptr<PerCameraROI>> roiMap;

    std::shared_ptr<PerCameraROI> getOrCreateROI(int camId) {
        std::lock_guard<std::mutex> lk(roiMapMtx);
        auto it = roiMap.find(camId);
        if (it != roiMap.end()) return it->second;
        auto p = std::make_shared<PerCameraROI>();
        roiMap[camId] = p;
        return p;
    }
};

2. 락 자체를 shared_ptr로 공유 소유

증상

카메라를 제거한 직후 프로그램이 비정상 종료될 수 있었습니다.

원인

기존 removeCamera()는 카메라는 제거할 때 락 객체까지 삭제했습니다. 하지만 이미 실행 대기 중인 비동기 작업이 이 락을 사용하려고 하면, 삭제된 객체에 접근하면서 오류가 발생할 수 있었습니다.

선택

카메라별 상태를 shared_ptr<PerCameraROI>로 공유 소유했습니다. 콜백은 시작 시점에 shared_ptr을 한 부 확보합니다.

효과

맵에서 제거된 이후에도 이미 실행 중이거나 대기 중인 비동기 작업에서는 해당 락을 안전하게 사용할 수 있도록 구조를 변경했습니다. 이를 통해 삭제된 객체에 다시 접근하는 문제를 방지했습니다.

3. 단방향 소유 트리로 순환 참조 제거

증상

종료 시 SDK·DB·파일 자원이 정리되지 않고 메모리가 반환되지 않았습니다.

원인

스트리밍 매니저와 카메라 매니저가 서로를 shared_ptr로 강하게 참조했습니다. 참조 카운트가 0이 되지 않아 소멸자가 영원히 호출되지 않습니다.

선택

소유 방향을 main → 컴포넌트 한 방향으로 강제하고, 컴포넌트끼리는 의존만 하되 역참조를 두지 않았습니다. 콜백에서 다른 객체가 필요하면 강한 멤버 대신 필요한 shared_ptr만 람다에 캡처합니다.

효과

누가 누구를 살려두는지가 한 방향으로 정리되어 lifetime 추적이 가능해졌고, 종료 시 자원이 순서대로 정리됩니다.

4. 처리 지연 시 중복 작업 제어

증상

클라이언트의 처리 속도가 느려지면 송신 대기 데이터가 계속 쌓여 메모리 사용량이 증가했습니다. 또한 이전 프레임의 분석이 끝나기 전에 같은 카메라의 다음 분석 작업이 다시 실행되는 문제가 있었습니다.

원인

송신 큐의 크기 제한이 없었고, 동일 카메라의 분석 작업이 동시에 실행되는 것을 막는 장치도 없었습니다.

선택

WebSocket 송신 큐에 최대 크기를 두고, 오래된 프레임은 버려 최신 프레임을 우선 전송하도록 변경했습니다.

효과

처리 지연이 발생해도 데이터가 계속 쌓이지 않아 메모리 사용량을 제한할 수 있었고, 동일 카메라의 분석 작업이 중복 실행되는 것도 방지했습니다.

auto& flag = getFlag(camId);
bool expected = false;
if (!flag.compare_exchange_strong(expected, true,
        std::memory_order_acquire, std::memory_order_relaxed))
    return;                          // 이전 프레임 처리 중 → 스킵

pool_.post([this, camId, frame = std::move(frame), cb = std::move(cb)]() mutable {
    Result result;
    try { result = processCamera(camId, frame, mountType); }
    catch (const std::exception& e) { LOG_ERROR(e.what()); }
    getFlag(camId).store(false, std::memory_order_release);  // 예외에도 반드시 해제
    if (cb) cb(std::move(result));
});

5. 락 보유 구간을 계산에서 떼어내기

증상

ROI 분석 중 같은 카메라의 다른 요청이 함께 지연됐습니다.

원인

락을 잡은 채로 CPU 집약 계산까지 수행하면 락 보유 시간이 계산 시간과 같아집니다.

선택

스냅샷 복사 → 락 없이 계산 → 결과만 반영, 3단계로 나눴습니다. 락은 앞뒤 두 구간에서만 짧게 잡습니다.

효과

락 보유 시간이 맵 복사·반영 비용으로 줄어 계산량과 분리됐습니다. 결과 반영 단계에서 상태가 실제로 바뀐 ROI만 이벤트로 승격시켜 불필요한 알림도 함께 줄였습니다.

// Step1 — 짧은 락으로 스냅샷만 복사

6. 장시간 동기 호출 앞에서 글로벌 락 해제

증상

한 대의 카메라가 재연결을 시도하는 동안 다른 카메라의 API까지 응답하지 않았습니다.

원인

SDK의 동기 connect는 대상이 응답하지 않으면 TCP timeout이 만료될 때까지, 약 34초간 반환하지 않습니다. 이 호출을 글로벌 락 안에서 수행하고 있었습니다.

선택

unique_lock으로 바꿔 SDK 호출 직전에 명시적으로 unlock하고, 진행 중인 이전 재연결 시도를 중단시킬 수 있도록 shared_ptr<atomic<bool>> abort 토큰을 도입했습니다.

효과

timeout이 흐르는 동안에도 다른 카메라의 콜백과 API가 정상 동작합니다. 새 connect가 시작되면 이전 재연결 스레드는 토큰을 확인하고 스스로 빠져나갑니다.

std::unique_lock<std::mutex> lk(globalMtx_);
// ... 기존 재연결 스레드에 중단 신호를 보내고 새 토큰 발급
reconnectAbort_[devIdx] = std::make_shared<std::atomic<bool>>(false);

// SicSdkSyncConnect 전에 lock 해제 — TCP timeout(~34초) 동안
// globalMtx_를 점유하면 다른 카메라의 onLogon/onClosed가 전부 막힌다
lk.unlock();
Def_DrErrCode syncRet = SicSdkSyncConnect(devIdx);

7. 콜백 중첩 대신 코루틴, write race 대신 strand

증상

비동기 흐름을 따라가기 어려웠고, 여러 경로에서 같은 WebSocket에 동시에 write를 시도할 수 있었습니다.

원인

accept 루프가 람다 안의 람다로 자기 자신을 캡처해 호출하는 형태였습니다. WebSocket은 한 번에 하나의 write만 허용하는데 이를 직렬화하는 장치가 없었습니다.

선택

Boost.Asio C++20 코루틴으로 비동기 로직을 선형 코드로 바꾸고, 세션마다 asio::strand를 둬 모든 write를 post했습니다.

효과

주기 작업이 별도 스레드 없이 io_context 안에서 실행되고, write는 strand로 자동 직렬화되어 프로토콜 위반 가능성이 사라졌습니다.

8. Python — async hub와 sync DB의 분리

증상

DB 쓰기가 지연되면 다른 hub의 메시지 수신까지 함께 밀렸습니다.

원인

asyncio 이벤트 루프 안에서 동기 SQLAlchemy를 호출하면 그동안 루프 전체가 멈춥니다.

선택

hub는 큐에 넣는 producer 역할만 하고, 별도 worker가 sync DB 작업을 전담하도록 분리했습니다. 큐는 카테고리별로 독립시켜 head-of-line blocking을 막았습니다.

효과

기존 sync 도메인 코드를 유지하면서 이벤트 루프를 보호했고, 큐 자체가 자연스러운 백프레셔 지점이 됐습니다. 비동기 전환에 드는 마이그레이션 비용도 피했습니다.

Python 관리 서버 설계

캐시 우선 갱신과 DB 비동기 처리

이벤트가 들어오면 캐시는 즉시 갱신하고 DB는 큐에 넣어 비동기 처리합니다. DB 처리량이 순간적으로 증가해 일부 저장 요청이 누락되더라도 캐시에는 최신 상태가 반영되어 있기 때문에 사용자 알림에는 영향을 주지 않습니다.

실시간 알람 시스템의 특성을 고려해 데이터 저장의 완전성보다 최신 상태와 알림의 즉시성을 우선하도록 설계했습니다. 이를 통해 DB 처리가 지연되는 상황에서도 알람 기능은 정상적으로 동작하도록 했습니다.

이벤트 진행 상태 관리 단순화

별도의 status 컬럼이나 is_active 플래그를 두지 않고, 종료 시각인 event_et이 NULL인지 여부로 진행 중인 이벤트를 판단했습니다. 이를 기준으로 동일 이벤트의 중복 생성을 방지하고, 감지 신호가 일정 시간 동안 들어오지 않으면 자동으로 종료 처리하도록 구성했습니다. 또한 서버가 비정상 종료된 뒤 재시작되는 경우에도 남아 있는 진행 중 이벤트를 동일한 기준으로 정리할 수 있도록 했습니다. 이벤트 상태를 여러 컬럼에 중복해서 저장하지 않아 상태 불일치 가능성을 줄이고, 관련 처리 로직도 event_et IS NULL이라는 하나의 기준으로 통일했습니다.

상태를 두 곳에 저장하면 반드시 어긋납니다. 표현 수단을 하나로 줄인 결과 도메인 규칙이 여러 함수로 흩어지지 않고 쿼리 조건 하나로 수렴했습니다.

카테고리별 큐 격리

큐와 worker를 카테고리별 1:1로 독립시켜 한 카테고리의 지연이 다른 카테고리를 막지 않도록 했습니다. 큐 하나에 모든 메시지를 담으면 head-of-line blocking이 발생합니다.

커넥션 풀 설정

worker 4개와 주기 루프, REST 핸들러가 동시에 접근하므로 pool 20 / overflow 40으로 잡고, pool_pre_ping으로 방화벽에 끊긴 stale 커넥션을 자동 폐기했습니다.

지수 백오프와 자동 재구독

C++ 서버가 재기동되어도 관리 서버는 살아 있어야 합니다. 3초에서 30초 cap까지 백오프하고, 재연결 직후 클라이언트가 구독했던 카메라를 자동 재구독해 단절을 감추었습니다.

Graceful Shutdown

알람 릴레이 → 외부 PLC → 내부 asyncio 워커 순으로 종료합니다. 각 단계에 타임아웃과 강제 cancel fallback을 뒀습니다.

열화상 파이프라인의 Python 이관

재설계로 C++ 서버는 안정화됐지만, 기능이 늘어날수록 C++ 단독으로 감당하는 비용이 커졌습니다. 복합 쿼리, 다중 클라이언트 세션 관리, FFmpeg 자식 프로세스 관리, Modbus·릴레이 보드 연동 같은 작업은 Python 쪽 생태계가 압도적으로 유리했습니다.

그래서 열화상 SDK 입력 자체를 Python이 직접 받도록 이관했습니다. 최종 운영에서는 citysafe-be-thermal.exe를 실행하지 않습니다.

SicSdk.lib는 Python이 로드하는 DLL이 아니라 MSVC 링커가 사용하는 정적 라이브러리입니다. 그래서 SDK를 감싸는 얇은 브리지 DLL을 따로 만들고, Python은 그 DLL만 로드합니다. 모든 함수는 extern "C"로 export해 name mangling을 피했고, 반환값은 0이면 성공, 음수면 오류이며 상세 메시지는 sic_get_last_error()로 조회하는 규약으로 통일했습니다.

SDK 콜백은 짧게 유지한다

벤더 SDK의 콜백 안에서는 JSON 생성, WebSocket 송신, Python 함수 호출을 일절 하지 않습니다. 콜백은 데이터를 native 상태에 기록하고 즉시 반환합니다. 콜백이 길어지면 SDK 내부 스레드를 점유하게 되고, 그 안에서 발생한 예외는 SDK 스택을 넘어가 프로세스를 종료시킬 수 있기 때문입니다.

Python 호출을 콜백에서 배제하면 GIL 획득 대기도 SDK 스레드에 전파되지 않습니다. 그래서 콜백과 소비자 사이를 공유 메모리로 끊었습니다.

공유 메모리 프레임 일관성 보장

카메라마다 shared memory와 named event를 하나씩 두고, 4개 슬롯을 순환하면서 ring buffer를 사용합니다. producer(C++ 콜백)와 consumer(Python)가 서로 다른 프로세스에 있으므로 뮤텍스를 공유할 수 없습니다. 대신 sequence 번호를 이용한 검증으로 찢어진 프레임을 걸러냅니다.

핵심은 슬롯을 쓰기 시작할 때 sequence를 0으로 낮추고, 다 쓴 뒤에 실제 값으로 올리는 것입니다. reader는 payload를 복사한 뒤 sequence를 다시 읽어, 복사 전후가 같을 때만 그 프레임을 채택합니다. 복사 도중 producer가 그 슬롯을 덮어썼다면 sequence가 달라지므로 버리고 재시도합니다. 

// producer (C++ 브리지)
const uint64_t sequence = ++next_sequence_;
auto* slot = slotAt((sequence - 1) % SIC_SHM_SLOT_COUNT);

InterlockedExchange64(&slot->sequence, 0);      // ① 쓰는 중 표시
slot->timestamp_ms = ...;                        // ② 메타 + payload 기록
for (size_t i = 0; i < count; ++i)
    output[i] = (static_cast<float>(input[i]) - 2731.0f) / 10.0f;

MemoryBarrier();                                 // ③ 기록이 먼저 보이도록
InterlockedExchange64(&slot->sequence, sequence);// ④ 슬롯 유효화
MemoryBarrier();
InterlockedExchange64(&header->latest_sequence, sequence);
SetEvent(event_);                                // ⑤ reader 깨우기
# consumer (Python)
if latest_sequence <= self._last_sequence:
    return None                                  # 새 프레임 없음

slot_offset = SHM_HEADER_SIZE + slot_index * slot_bytes
sequence, timestamp_ms, w, h, pixel_type, payload_bytes = SHM_SLOT.unpack(...)
if sequence != latest_sequence:
    continue                                     # 이미 덮어써짐 → 재시도

payload = self._mapping.read(payload_bytes)      # 복사
self._mapping.seek(slot_offset)
sequence_after = struct.unpack("<Q", self._mapping.read(8))[0]
if sequence_after != sequence:
    continue                                     # 복사 중 덮어써짐 → 재시도

temperature = np.frombuffer(payload, dtype="<f4").reshape((h, w)).copy()

MemoryBarrier()가 없으면 컴파일러나 CPU가 “payload 기록”과 “sequence 갱신”의 순서를 바꿀 수 있고, 그러면 reader가 아직 덜 쓰인 슬롯을 유효하다고 판단합니다. 이 검증 방식 덕분에 reader는 락을 전혀 잡지 않고, writer 뮤텍스도 카메라별로 분리되어 다른 카메라의 수신을 막지 않습니다.

수신 속도가 처리 속도보다 빠르면 오래된 프레임이 자연스럽게 drop되고 최신 프레임이 우선됩니다. C++ 서버의 MAX_QUEUE=2 정책과 같은 판단입니다.

C++ → Python 단계적 이관

운영 중인 시스템이었기 때문에 전체 기능을 한 번에 전환하지 않고, 기능 단위로 Python에 이관했습니다. 기존 C++ 로직과 병행 운영하며 결과를 비교한 뒤, 동작이 검증된 기능부터 C++ 측 처리를 순차적으로 비활성화했습니다.

ROI 연산이 Python으로 이전되면서 C++의 ROI 전용 스레드 풀을 제거했고, 현재 C++ 브리지는 SDK 데이터 수신과 공유 메모리 기록에 집중하도록 역할을 단순화했습니다. 각 단계별로 기존 처리 경로를 유지한 상태에서 검증한 뒤 전환해, 문제가 발생하더라도 이전 방식으로 되돌릴 수 있도록 구성했습니다.

트러블슈팅

녹화 파일 길이 일관성 유지

이벤트가 종료되는 즉시 녹화를 중단하면 마지막 녹화 파일의 길이가 매번 달라질 수 있습니다. 운영자가 영상을 확인할 때 파일 단위가 일정하도록, 이벤트가 종료되더라도 다음 5분 구간까지 녹화를 유지한 뒤 종료하도록 구성했습니다.

그래서 이벤트가 끝나도 다음 5분 경계까지 채운 뒤 stop하도록 예약합니다. 경과 시간 계산에는 time.monotonic()을 썼습니다. 벽시계는 NTP 동기화로 뒤로 갈 수 있어 경과 시간 측정에 쓸 수 없습니다. 종료는 terminate 후 10초 대기, 그래도 안 되면 taskkill /T /F 순으로 처리해 trailer가 정상적으로 쓰이도록 했습니다.

안전한 서버 종료 및 릴레이 초기화

서버가 종료되는 과정에서 릴레이가 ON 상태로 남으면 현장의 경광등이나 사이렌이 계속 동작할 수 있습니다. 이를 방지하기 위해 서버 종료 시 알람 릴레이를 가장 먼저 OFF 처리한 뒤 외부 장치 연결과 내부 작업을 순차적으로 종료하도록 구성했습니다.

서버 시작 시에도 모든 릴레이 채널을 OFF 상태로 초기화해 이전 실행의 비정상 종료로 남아 있을 수 있는 상태를 제거했습니다. 이후 실제 알람 조건이 유지되고 있다면 다음 감지 주기에서 다시 정상적으로 활성화되도록 했습니다.

Windows 환경의 DB 연결 오류 대응

Windows의 CP949 환경에서 psycopg2가 비밀번호 파일 경로를 확인하는 과정에서 인코딩 오류가 발생하는 문제가 있었습니다.

해당 기능을 사용하지 않는 환경에서는 PGPASSFILE을 NUL로 지정해 불필요한 파일 탐색을 막았습니다. 또한 os.environ.setdefault()를 사용해 배포 환경에 이미 설정된 값이 있는 경우에는 기존 설정을 유지하도록 했습니다.

설계 원칙

실시간 모니터링 시스템의 특성을 고려해 과거 데이터의 완전성보다 최신 상태와 빠른 복구를 우선했습니다. 이를 기준으로 큐 크기를 제한하고 오래된 데이터를 폐기했으며, 재연결 백오프와 안전한 종료 순서를 적용했습니다. C++과 Python 영역에서도 동일한 기준을 적용해 장애나 처리 지연 상황에서 일관된 방식으로 동작하도록 구성했습니다.

또한 발생한 오류를 개별적으로 수정하기보다 문제를 만드는 구조 자체를 개선하는 방향으로 접근했습니다. 공유 데이터마다 동기화 범위를 명확히 하고, 여러 락이 필요한 구조는 단순화해 교착 상태 가능성을 줄였습니다. 객체 간 참조 관계도 한쪽 방향으로 정리해 수명 관리 과정에서 발생할 수 있는 잘못된 메모리 접근을 방지했습니다.
