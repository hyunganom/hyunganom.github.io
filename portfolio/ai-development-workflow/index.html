01. 배경과 문제

city_safe는 API·웹소켓, 주차 처리, 예측 서버, DB·캐시·백그라운드 큐가 연결된 시스템입니다. 첫 규칙 적용 대상인 managing_server는 Python, FastAPI, SQLAlchemy, Pydantic, pytest를 사용했습니다.

요청마다 달라지는 개발 맥락

로그·예외 처리, 캐시 활용, API 오류 규칙을 반복해서 설명해야 했습니다. 공통 기준이 충분하지 않아 생성된 코드의 구현 방식과 확인 범위를 일관되게 관리하기 어려웠습니다.

코드 작성 이후에 남는 검증

API가 성공 응답을 반환해도 DB 저장, 캐시 반영, 큐 소비와 장비 반영이 모두 끝났다고 볼 수 없었습니다. 실패 시 남는 상태와 사람이 실행할 QA 절차를 따로 확인해야 했습니다.

02. 공통 규칙과 작업별 절차를 나눠 설계

개별 로그·예외 처리 스킬을 늘리기 전에 프로젝트의 기본 규칙부터 정리하기로 했습니다. 제가 문제와 적용 범위, 검토 기준을 정의하고 AI와 함께 문서·스킬을 설계·작성·검토했습니다.

AGENTS.md — 모든 변경에 참고할 공통 기준

선택 이유

매번 전달하던 지침을 프로젝트에 남겨, 기능이 달라져도 같은 기준으로 기존 구현과 변경 영향을 확인하도록 했습니다.

적용 범위

새로 작성하거나 수정하는 코드에 우선 적용하고, 기존 코드는 해당 기능과 관련된 범위에서 점진적으로 확인하도록 정했습니다.

Agent Skill — 특정 작업을 반복할 때의 절차

선택 이유

동시성 검토와 QA 문서 작성은 확인할 근거와 산출물이 달랐습니다. 각각의 분석 순서와 결과 형식을 스킬로 묶어 재사용하도록 했습니다.

적용 범위

관련 변경에 동시성 검토 스킬을 활용하고, QA 문서 작성은 요청이 있을 때 수행하도록 구성했습니다.

Notion MCP — QA 문서 게시와 결과 조회

선택 이유

사람이 QA 절차를 읽고 실행 결과를 남길 공간이 필요했습니다. 기존 Notion MCP 서버를 연동해 문서를 게시하고, 게시 내용을 다시 조회해 확인했습니다.

역할 구분

QA 항목을 설계하는 절차는 스킬에 두었습니다. 문서는 Markdown으로도 작성할 수 있으며, MCP는 외부 문서 도구에 연결하는 수단으로 사용했습니다.

03. 구현한 규칙과 검토 절차

A · 프로젝트 개발 지침

변경 전 확인부터 완료 보고까지 명시

managing_server/AGENTS.md에 기존 구현·스키마·공통 함수·테스트를 먼저 확인하도록 정리했습니다. API 오류는 기존 오류 카탈로그를 참조하고, 코드·응답 형식·상태 코드를 임의로 바꾸지 않도록 했습니다.

  • 캐시 판단: DB 조회 전에 캐시 활용 가능성을 검토하되, 최신성·트랜잭션·잠금·공유 객체 여부를 기준으로 적합성을 판단합니다.
  • 실패 단계 확인: DB 쓰기·commit, 캐시 반영, 큐 등록·소비, 외부 호출을 구분하고 롤백·자원 정리와 실패 후 남는 상태를 확인합니다.
  • 로그와 완료 보고: 기존 로거로 대상·작업·실패 단계·결과를 남기고 민감 정보 노출을 확인합니다. 테스트 결과, 미검증 사항과 정책 미정 사항을 함께 기록합니다.

기존 API 오류 문서는 복제하지 않고 참조했습니다. 요청과 무관한 전체 리팩터링으로 확대하지 않으며, 조사·검토와 구현 변경을 구분하도록 했습니다.

B · city-safe-concurrency-review

처리 지연·누락·순서 문제를 코드 근거로 검토

주차 처리와 예측 서버, 연결된 DB·큐를 첫 대상으로 삼았습니다. SKILL.md에 검토 절차를, references/runtime-map.md에 실행 경로를 정리했습니다.

  • 공유 상태와 잠금 범위, 작업 순서·중복 처리, 비동기 함수 안의 동기 DB·파일·추론 작업을 확인합니다.
  • 큐 용량·포화 시 동작, 저장 실패·재시도·트랜잭션, 서버 간 전달과 재시작·재전송을 연결된 생산자·소비자까지 추적합니다.
  • 결과는 발생 조건 → 코드 위치 → 영향 → 검증 방법 → 개선 방향으로 작성합니다.

코드에서 확인한 사실, 조건부 위험, 테스트 재현 결과, 운영 환경에서 추가 측정할 부분을 구분하도록 설계했습니다.

C · city-safe-notion-qa

사람이 실행하고 결과를 기록할 수 있는 QA 문서

라우터 등록과 실제 경로, 요청·응답 스키마, 오류 카탈로그를 분석하고 서비스·DB·캐시·큐·장비 호출과 웹소켓 흐름까지 확인하도록 구성했습니다. 작성 절차와 references/qa-template.md의 공통 양식을 함께 사용했습니다.

  • 실행 준비: ID·목적·우선순위·준비 조건과 HTTP 요청 예시 또는 웹소켓 접속·송신 메시지를 작성합니다.
  • 판정 근거: 순서별 절차, 예상 응답, DB·로그·화면 확인 위치와 코드·문서 근거를 명시합니다.
  • 실행 기록: 데이터 정리·복구 절차와 실제 결과·증거·담당자·실행 시각 기록란을 둡니다. 회차마다 새 페이지를 만들어 이전 기록을 보존하도록 했습니다.

API 성공과 DB·캐시·장비 반영 완료, 웹소켓 연결·구독 응답과 실제 수신을 각각 구분했습니다. 현재 구현을 요구사항으로 단정하지 않고, 기대 동작이 불명확하면 ‘정책 확인 필요’로 남겼습니다. 모든 항목은 ‘미실행’으로 시작합니다.

Notion 연동은 실제 도구 호출과 게시 내용까지 확인

CLI를 찾지 못하는 문제를 해결한 뒤 기존 Notion MCP 서버 등록과 OAuth 로그인을 완료했습니다. 설정상 활성화되어 있어도 현재 세션에서 도구를 사용할 수 없는 경우가 있어, 등록 상태와 세션의 도구 사용 가능 상태를 나눠 확인했습니다. 이후 QA 페이지 조회, 문서 게시, 게시 내용 재조회까지 확인했습니다.

기존 MCP 서버를 연동해 활용한 작업이며, MCP 서버 자체를 개발한 것은 아닙니다.

동시성 검토 시범 적용에서 확인한 조건

검토 당시 기존 관련 테스트 38개가 통과했습니다. 이와 별도로 격리된 재현을 통해 다음 세 가지 위험 조건을 확인했습니다.

  1. 느린 동기 DB 저장 → 다른 비동기 작업 지연

    저장이 오래 걸리는 조건에서 다른 비동기 작업도 지연되는 경우를 확인했습니다.

  2. 큐 포화 → 주차 작업 누락 후 재등록 실패

    큐 포화로 빠진 주차 작업이 같은 입력에서 다시 등록되지 않는 경우를 확인했습니다.

  3. 선행 outbox 이벤트 실패 → 후속 알람 대기

    선행 이벤트가 계속 실패하면 후속 알람 처리가 대기하는 경우를 확인했습니다.

38개는 새로 작성한 테스트 수가 아닙니다. 위 결과는 위험 조건을 확인한 범위이며, 발견한 문제의 전체 수정이나 운영 성능 개선 완료를 의미하지 않습니다.

05. 검증 범위와 한계

이번 작업에서 확인한 범위

  • 개발 지침 1개와 작업별 스킬 2개 구성
  • 실제 두 기능에 QA 시나리오 50개 작성·게시 및 게시 내용 확인
  • 동시성 검토 당시 기존 테스트 38개 통과
  • 격리된 환경에서 지연·누락·순서 관련 위험 조건 재현

후속 검증이 필요한 범위

  • 실제 서버·DB·장비를 대상으로 한 수동 QA 실행
  • 발견한 위험의 개선 적용과 변경 후 재검증
  • 운영 부하·최대 처리량·지원 카메라 수 측정
  • 개발 시간 절감과 품질 개선 효과 측정

문서와 스킬은 검토 기준과 절차를 제공하는 산출물입니다. 린터·포매터·CI 강제 검사, 자동 테스트 실행 또는 상시 모니터링 체계를 구축한 범위는 아닙니다.

06. 반복되는 요구부터 단계적으로 적용

  1. 2026.11.04
    기본 규칙부터 정리

    로그·예외 처리 스킬 초안을 검토한 뒤 공통 기준을 우선하기로 결정하고, managing_server의 AGENTS.md를 작성했습니다.

  2. 2026.11.05
    검토·QA 스킬 구성과 첫 적용

    동시성 검토 스킬을 시범 적용하고 QA 작성 스킬과 Notion 연동을 구성했습니다. 세션 도구 사용을 확인한 뒤 장비 기능 QA 29개를 게시했습니다.

  3. 2026.11.11
    다른 기능에 재사용

    가스 기능 QA 21개를 게시하고, Markdown 문서 작성과 Notion 게시·조회가 맡는 역할을 구분해 정리했습니다.

날짜는 한국 시간 기준입니다. 초기 로그·예외 처리 스킬은 후보 초안으로 남겼으며, 완성한 스킬 2개에 포함하지 않았습니다.

07. 회고 — 생성 이후의 확인 절차까지 설계

AI에 같은 지시를 반복하는 과정에서, 프로젝트 전체에 적용할 기준과 특정 작업의 수행 절차를 분리할 필요를 확인했습니다. 모든 도구를 먼저 만드는 대신 실제 작업에서 반복되는 요구를 기준으로 규칙과 스킬을 구성했습니다.

코드가 생성됐다는 사실보다 어떤 처리 단계가 끝났고, 실패하면 무엇이 남으며, 사람이 어디서 결과를 확인할지를 명시하는 것이 중요했습니다. QA 문서도 사람이 실행하고 판정할 수 있는 형태를 목표로 설계했습니다.

Notion은 문서 공유와 실행 기록을 위한 선택이었습니다. 규칙과 스킬만으로 동작의 정확성이 보장되지는 않으므로, 실제 테스트와 사람의 검증을 후속 단계로 남겼습니다.
